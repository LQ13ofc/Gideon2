## Decisões

1. **Token do GitHub**: a conta `github` sem fake usa o fluxo de token (como o Home Assistant): `connection_connect` põe a
   conta em `connecting`, `connection_consent` concede escopos, `connection_set_token` faz uma única sonda `GET /user`
   (cabeçalhos `Accept: application/vnd.github+json`, `X-GitHub-Api-Version`, `User-Agent`). O `login` devolvido vira o
   `account_ref`. O token fica só em memória até a sonda responder e então no cofre `conn:<id>:access` (0600). Nunca aparece
   em snapshot, ledger, auditoria ou log (teste: o snapshot não contém o token).
2. **Escopos e operações GitHub reais**: `repo:read`, `issues:write`, `pulls:write`, `user:read`, `notifications:read`.
   Operações (12): `user.get` (`/user`), `notifications.list` (`/notifications`), `repos.list` (`/user/repos`), `repo.get`,
   `issues.list`, `pulls.list`, `pulls.get`, `actions.list` (`/repos/{repo}/actions/runs`, lista `workflow_runs`),
   `issues.create`, `issues.update`, `issues.comment`, `pulls.comment`.
3. **Escritas perigosas com confirmação**: `issues.create`, `issues.comment` e `pulls.comment` têm risco `public`
   (cartão de confirmação obrigatório, nunca executam sem `tool_decide` autorizar). `issues.create` só vira `write` quando
   `repo.get` já mostrou o repositório como privado. Sem reenvio em falha: `issues.create` e comentários não são idempotentes.
4. **Guarda `--connections-allow-public` só para fakes**: o interruptor de teste bloqueava toda ação pública. Agora ele vale
   apenas quando o provedor tem fake (`has_fake`). Um backend real exige apenas a confirmação do cartão.
5. **Caminhos reais**: o fake mantém seus caminhos `/api/...` (gates existentes). O GitHub real usa `github_real_template`
   (um caminho por operação, preenchido com valores validados). Teste: todas as 12 operações têm caminho real.
6. **MCP real (CONN-04)**:
   - Registro do dono: `<data-dir>/mcp-servers.json` (somente leitura para o Core, até 8 KiB, versão 1, `deny_unknown_fields`).
     Cada servidor: `name` (id simples, único), `script` (caminho absoluto de arquivo existente) e `scopes` (opcional; padrão
     `mcp.discover` e `mcp.call`; `mcp.call_destructive` só se declarado). Os escopos declarados são o teto do
     consentimento (privilégio mínimo). Registro inválido: nenhum servidor real sobe.
   - A conta MCP real leva o nome do servidor registrado no `label`. Nome desconhecido: `invalid_connection`.
   - O processo roda no sandbox de plugin (`bwrap --unshare-all`, sem rede, ambiente limpo, raiz somente leitura, capacidades
     zeradas, `prlimit`), pelo mesmo `mcp::start` do E2.4. O argumento `--profile good` é só a etiqueta de lançamento que
     `mcp::start` sempre passa; o servidor real a ignora.
   - Confiança: toda ferramenta nova ou alterada, inclusive a primeira lista, fica `needs_reapproval` e aparece com risco
     `destructive` (perigosa) até o dono confiar nela por ferramenta (`connection_trust_tools`). Chamada de ferramenta não
     confiável: `tool_not_trusted`, sem cartão e sem rede. Descoberta feita por skill nunca confia.
   - Exceção deliberada: o registro de teste `--connections-fake-mcp` mantém o comportamento E2.4 (a primeira lista do
     dono é confiada) para os gates existentes. Servidor real nunca confia automaticamente.
7. **Google e Home Assistant**: sem backend real, `connection_connect` responde `real_backend_unsupported` (mesmo código
   que o cliente já conhece) e nada é aberto. Estado descrito por `connections::readiness(provider)`:
   `pronto, aguardando credenciais`. O snapshot não ganhou campo novo: a validação estrita de `app/bridge.py` recusaria o
   bloco inteiro (ver Patches).
8. **Visual fallback (CONN-06), política**: a rota visual substitui uma API só quando (a) não existe conta utilizável
   (`Standing::NoBackend`, `NoAccount` ou `Disconnected`), (b) o dono ligou o fallback para a finalidade e (c) a publicação
   foi aprovada. Conta com token expirado, reautenticação, escopo ausente, em conexão, offline ou com erro nunca cai no visual.
   Falha de chamada da API (429, 403, 5xx) também não abre o visual. Implementada como função pura
   `visual_fallback_allowed(standing, enabled, approved)`.

## Patches necessários fora deste pacote (não aplicados por regra de arquivo)

### 1. WP-6: `scripts/net_broker.py` (obrigatório para GitHub real funcionar)

```diff
-ALLOWED_HEADERS = {"content-type", "accept", "idempotency-key"}
+ALLOWED_HEADERS = {"content-type", "accept", "idempotency-key", "user-agent", "x-github-api-version"}
```

Motivo: GitHub exige `User-Agent` (verificado: 403 sem, 200 com). `X-GitHub-Api-Version` é opcional, mas a versão fixa
evita mudança de resposta.

### 2. WP-6: `scripts/net_broker.py` (opcional: só para a leitura pública sem token do self-test)

```diff
-    if keyless and (ip is None or not ip.is_loopback):
+    if keyless and request["allow_loopback"] and (ip is None or not ip.is_loopback):
```

Motivo: `keyless` deve restringir apenas alvos locais (com `allow_loopback`). Sem chave, um alvo de nuvem recebe um pedido
sem `Authorization`. O Core nunca monta isso para nuvem (`broker::payload` recusa `key_missing` antes). IP LAN continua
recusado pela regra de IP literal não-loopback. Sem este patch, o item do dono "leitura pública via broker" permanece
BLOQUEADO.

### 3. WP-17: `src/registry.rs:577`

`crate::connections::has_fake("github")` → `crate::connections::has_backend("github")`.
Sem isso, o registro considera o GitHub real inexistente (`no_api`), e o fallback visual passaria a ser elegível sem
necessidade. Além disso, `registry.rs` deve chamar `connections::visual_fallback_allowed(standing, enabled, approved)`
na decisão do fallback (CONN-06).

### 4. WP-17: `src/core.rs:1666` e `src/agent.rs:733` (decisão do dono)

Uma proposta de agente com risco `public` (`github_create_issue`, `pulls.comment`) só roda com
`--agent-allow-destructive`. Cartões abertos pela UI não dependem disso. Recomendação: manter desligado por padrão; o dono
liga o interruptor se quiser que o agente proponha issues (cada uma continua pedindo confirmação).

### 5. WP-17: `app/bridge.py` e UI (para o dono usar)

- Entrada do token do GitHub na página Conexões (hoje só o Home Assistant tem campo de token): `connection_set_token`
  já aceita o token do GitHub.

## Como o dono roda o self-test

Coloque o token de GitHub num arquivo seu, fora do repositório, com permissão 0600 (ex.: `~/.config/gideon/connectors/github.token`),
e rode:

```
python3 -I scripts/connector_selftest.py github-token --token-file ~/.config/gideon/connectors/github.token
python3 -I scripts/connector_selftest.py homeassistant --url https://SUA-INSTANCIA --token-file ~/.config/gideon/connectors/ha.token
python3 -I scripts/connector_selftest.py google --credentials ~/.config/gideon/connectors/google.json
python3 -I scripts/connector_selftest.py mcp --script /caminho/absoluto/do/servidor.py
```

Saída: uma linha JSON por verificação; exit 0 = passou, 2 = aguardando credenciais, 1 = falhou ou bloqueado (o motivo vem na
linha). Nenhum token, cabeçalho ou corpo de resposta é impresso.

Registro de servidores MCP reais (arquivo `mcp-servers.json` dentro do diretório de dados do Core, o `--data-dir`):

```json
{"version": 1, "servers": [{"name": "notas", "script": "/abs/servidor.py", "scopes": ["mcp.discover", "mcp.call"]}]}
```

A conta MCP deve ser criada com `label` = `notas`. Depois de conectar, confie em cada ferramenta na página Conexões
(`connection_trust_tools`); ferramentas de servidor nunca são confiáveis sozinhas.
