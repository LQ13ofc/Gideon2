# S4 — Skill Engine, Skill Creator e Skill Sharing (D1–D4)

Fonte: Notion "S4 · Skill Engine e compartilhamento". Premissa: NÃO existe catálogo de skills da
equipe; só o motor, o criador e o compartilhamento. Fixtures sintéticas ficam em `tests/fixtures/`
e nunca são entregues. Skill = procedimento declarativo que combina capacidades já instaladas; não
é código, não concede permissões, não executa shell nem JS/Python.

## D1 — Manifest/DSL (arquivo `skill.json`, ≤ 16 KiB, UTF-8, `deny_unknown_fields`)

```
{ "schema_version": 1,
  "id": "^[a-z][a-z0-9_]{2,40}$", "name": str≤64, "version": "semver",
  "publisher": {"id": "^[a-z][a-z0-9_-]{2,40}$", "name": str≤64},
  "description": str≤512, "license": str≤32, "min_runtime": "0.1.0",
  "triggers": [str≤64] (≤5, só sugestões; nunca wake direto),
  "inputs":  { name: {"type":"string|int|bool","required":bool,"default"?,"max"?:int,"min"?:int} } (≤8),
  "outputs": { name: {"type":"string|int|bool"} } (≤8),
  "dependency_capabilities": [capability_id | tool:<nome>] (≤8),
  "permissions_required": [str] (≤8; INFORMATIVO: grants só vêm do Core/usuário),
  "prerequisites": [str≤128] (≤4),
  "steps": [ {"id":"^[a-z][a-z0-9_]{0,23}$", "call": capability_id | "tool:<nome>" | "skill:<id>",
             "args": objeto (profundidade ≤3, ≤2 KiB), "when"?: cond, "unless"?: cond,
             "retries"?: 0..=2, "timeout_ms"?: 1..=10000, "idempotent"?: bool,
             "verify"?: cond, "undo"?: {"call","args"}, "save"?: {out_name: "field"}} ] (1..=16),
  "attestations": [{"kind": str≤32, "text": str≤128}] (≤4),
  "readme": str≤2048 (opcional) }
cond = {"ref": "input.x" | "steps.<id>.<campo>", "op": "eq|ne|exists|gt|lt", "value"?: escalar}
```
Templates em strings de `args`: somente `${input.x}` e `${steps.<id>.<campo>}` (referência a passo
ANTERIOR); nenhuma expressão. Regras de rejeição (validator, códigos `skill_invalid:<motivo>`):
`schema_version` ≠ 1; `min_runtime` > runtime; chaves desconhecidas; `call` fora de
`dependency_capabilities` (out_of_scope); id de passo duplicado; ref a passo futuro/inexistente;
ciclo/recursão (`skill:` para si mesma ou ciclo entre skills instaladas) e profundidade de skill
aninhada > 2; mais que 16 passos / 8 deps / limites de tamanho; string de `args` que parece caminho
(`^/`, `..`, `~`), URL (`://`), shell (`;`, `|`, `$(`, crases), ou nome de segredo (`key`, `token`,
`secret`, `password` como chave de args) ⇒ `exfiltration`; campo de grant/permissão dentro de steps;
capability reservada de Base (`base.`, `core.`, `system.`, `safety.`); dependência ausente NÃO invalida
o manifest, bloqueia a execução (`missing_dependency`) e é listada no preview.

Emenda D1: `triggers`, `inputs`, `outputs`, `dependency_capabilities`, `permissions_required`, `prerequisites`,
`attestations` e `readme` são opcionais (default vazio); `schema_version, id, name, version, publisher, description,
license, min_runtime, steps` são obrigatórios.

## Estados e armazenamento

Estados: `draft → validated → tested → approved → enabled | disabled | revised`. Ledger privado
`skills.json` (0600, version 1, `revision` CAS, ≤ 32 KiB, deny_unknown_fields, mesmos guards do
hub-installed): `{id, versions:[{version, manifest_sha256, state, source: created|imported|llm_draft,
approved_at_rev?}], active: version|null}`; manifests em `skills/<id>/<version>/skill.json` (0600,
≤ 3 versões por skill, ≤ 16 skills). Ledger `skill-runs.json` (≤ 32 execuções, sem conteúdo: id da
execução, skill, versão, estado, passo falho, códigos). Só a ação do USUÁRIO (ops do socket) move
`tested → approved` e `approved → enabled`.

## D2 — Executor (Core, `src/skills.rs`)

Ops (estritas, versionadas, dedup): `skill_validate{manifest}` (não grava), `skill_save_draft{manifest}`,
`skill_dry_run{id,version,inputs}` (RESOLVE_DEPS + CHECK + PREVIEW + resolve templates; ZERO chamadas a
capabilities; sucesso marca `tested`), `skill_approve{id,version,revision}`, `skill_enable/disable{id,revision}`,
`skill_rollback{id,revision}` (volta a versão anterior), `skill_remove{id,revision}`, `skill_run{id,inputs}`,
`skill_decide{run_id,step,decision}` (aprovar passo que muda estado, como tool_decide), `skill_cancel{run_id}`.
Pipeline: RESOLVE_DEPS (todas as dependências existem: plugin da capability em `running` ou tool no
registro) → CHECK_PERMISSIONS (skill `enabled`; permissões do plugin dono APROVADAS no Core; `permissions_required`
só informativo; nada é elevado) → PREVIEW (snapshot lista passos/risco) → RUN_STEP (capability_invoke
interno ou tool do registro fixo C1/C3/C4; passos de risco `state_changing` exigem `skill_decide`; destrutivo
nunca executa em dev) → VERIFY (`verify` cond sobre saída; falha ⇒ falha do passo) → em falha: retries
limitados, depois COMMIT/ROLLBACK (executa `undo` dos passos concluídos em ordem inversa, ≤ 8, cada um com timeout)
→ REPORT. Limites: 1 run por vez, ≤ 16 passos, run ≤ 60 s, `skill:` aninhada ≤ 2. Cancel aborta o passo em voo
(`capability_cancel`) e roda undo. Revogar plugin dono ⇒ run falha `missing_dependency` + rollback.
Snapshot `skills`: `{revision, items:[{id,name,version,state,source,active,deps_ok,permissions_ok,missing:[…]}], run: null|{run_id,skill,state,step,steps:[{id,state,code?}],outputs?}, history:[…]}`; saídas ≤ 1 KiB, sem args brutos.

## D3 — Criador por LLM (plugin `llm_engine` 1.2.0; capability `llm_engine.skill_draft`)

Entrada `{description ≤1024, name?}`. O plugin usa o chat do provedor (no gate: script/`agent_script`), pede um
manifest JSON, e chama HOST SERVICES do Core (permissão aprovada `skills_author`): `skills.validate{manifest}`,
`skills.draft_put{manifest}` (cria SOMENTE `draft`/`llm_draft`), `skills.dry_run{id,version,inputs}`, `skills.list{}`.
Saída: `{draft_id, version, state, requirements[], ambiguities[], preview[{id, call}], validation?{ok:true}, diff?}` (Emenda S4 gate final: `preview` tem um `{id, call}` por passo do manifest e `validation` é o resultado do `skills.validate`; a Base aceita ambos; ambiguidades são texto PlainText). Serviços inexistentes para plugin:
`skills.approve/enable/export/publish/run` ⇒ `unknown_service`/`permission_denied`; `draft_put` nunca pode
substituir versão `approved/enabled` (cria nova versão `revised` em draft). O modelo, por qualquer prompt/injeção,
não consegue autopublicar ou autoaprovar; o gate prova isso ao vivo com script malicioso.

## D4 — Compartilhamento (pacote `.gskill`)

`skill_export{id,version}` ⇒ arquivo `<home>/skill-exports/<id>-<version>.gskill` (JSON: `{format:1, manifest, readme,
license, author, version, files:[{path,sha256}], package_sha256, publisher_id, signature:null}`). SEM segredos, caminhos
do usuário, histórico ou memória. Assinatura de publisher NÃO é implementada (sem dependência criptográfica aprovada):
`signature` é sempre `null`, publisher aparece como "não verificado"; integridade = sha256. `skill_import{name}` lê SÓ
de `<home>/skill-imports/<name>.gskill` (nome `^[A-Za-z0-9._-]{1,64}$`, arquivo regular, ≤ 64 KiB, O_NOFOLLOW), faz
scan (validator D1, varredura de caminhos/segredos, hash do pacote e dos arquivos, ID duplicado, compat. `min_runtime`)
e gera PREVIEW no snapshot (`import:{name,id,version,publisher,unverified:true,permissions_required,missing_deps,
permission_delta,duplicate,findings[]}`); `skill_import_confirm{name,revision}` instala como `draft` (re-aprovar; NUNCA
concede grants). Update de versão mostra `permission_delta` e `permissions_escalated:true` quando cresce; versões
anteriores ficam para rollback. Negativos: path malicioso, manifest adulterado (hash), pacote corrompido, escalada de
permissões, ID duplicado, arquivo gigante/symlink. Ratings: NÃO implementados.

## UI (Qt) — aba "Skills"

Lista com estado/versão/deps; Criar (descrição → "Gerar com LLM" só se o plugin LLM roda; editor JSON manual sempre);
Validar, Simular (dry-run), Aprovar, Habilitar/Desabilitar; Versões/Rollback; Permissões (necessárias × aprovadas ×
faltando); Importar (preview + achados + delta) / Exportar; Executar com progresso, aprovação por passo, Cancelar,
detalhe de erro; Histórico. Tudo PlainText; sem LLM, skills determinísticas instaladas executam.

## Gates

`verify_d1_skill_dsl.py` (validator + negativos), `verify_d2_skill_run.py` (Core real; fixtures leitura→processamento→
escrita sintética via mundo C4/C3; erro no passo 2 ⇒ rollback; cancel; dependência perdida; sem efeito fora do mundo;
sem elevação), `verify_d3_skill_llm.py` (LLM roteirizado cria, valida, simula; tentativas de autoaprovar/publicar por
injeção negadas), `verify_d4_skill_share.py` (A cria→exporta→B importa sem segredos→deps→autoriza→executa→remove;
negativos), `verify_s4_final.py` (Qt Skills, regressão S1–S3). Matriz completa uma vez ao fim do S4.
