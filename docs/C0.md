# S3 / C0 — runtime de plugins, capability registry e revogação

Fonte: Notion "S3 · Plugins e LLM Engine" (Gate C0). C0 passa somente com um
plugin dummy que resolve uma capability real no Core e pode ser revogado, sem
quebrar S1/S2. Nada de LLM, Model Manager, rede, tela, mouse, microfone avançado.
Plugins não substituem Safety, não concedem permissões e não fazem bypass.

## Escopo C0.1 (Core) / C0.2 (UI+pacote) / C0.3 (gate)

Pipeline: manifest → Hub instala (B3.3) → UI de permissões (B3.2a) → **Ativar**
(novo) → Core recebe capability → cliente invoca → plugin sandbox responde →
Core valida → **Revogar/Desativar** → capability some → remover → regressão S1/S2.

## Manifest (campos novos, OPCIONAIS)

`runtime`: `"python3_script"` (único valor em C0); `capabilities`: lista de ids.
Ambos `#[serde(default, skip_serializing_if)]` para NÃO mudar manifest_sha256 de
manifests existentes. Regras: capability id `^[a-z0-9_]+(\.[a-z0-9_]+)+$`, ≤ 64
chars, ≤ 8 por plugin, DEVE começar com `<plugin_id>.`; namespaces reservados
(`base.`, `core.`, `system.`, `safety.`, `llm.`, `screen.`, `computer.`, `audio.`,
`mic.`, `camera.`, `display.`): uma capability é reservada quando seu PRIMEIRO segmento
(antes do primeiro ponto) é uma dessas palavras; um plugin_id é reservado só quando é IGUAL a
uma delas. Assim `llm_engine` e `llm_engine.chat` são permitidos; `llm.chat` e `core.x` não.
Sem `runtime` → payload opaco, `plugin_enable` recusa (`plugin_not_runnable`).
`entrypoint` continua relativo; em C0 o payload (arquivo único, hash pinado) é o
script. Catálogo com capability inválida → catálogo em quarentena (fail closed).

## Estado de plugin (ledger privado `plugin-state.json`)

≤16KiB, version 1, `revision` CAS própria, deny_unknown_fields, 0600, mesmos guards
de hub-installed.json. `enabled: [plugin_id…]` (≤8). Habilitado só se: instalado
verified (não quarantined), approval exata vigente para o MANIFEST ativo, runtime
suportado. Update de versão (manifest diferente) ou perda de approval ⇒ plugin sai
de `enabled` (re-ativação explícita). Rollback também revalida.

## IPC (mesmos dedup/unknown fields/versão/Ready; sessão de voz ativa → `busy`)

- `plugin_enable{revision, plugin_id}`; `plugin_disable{revision, plugin_id}`;
  `plugin_revoke{revision, plugin_id}` = disable + remove approval do plugin
  (approval_revision+1) + mata processo; reativar exige nova aprovação.
  `revision` = `plugin_revision` do snapshot. Erros: stale_plugin_revision,
  unknown_plugin, plugin_not_runnable, plugin_quarantined, permissions_not_approved,
  not_installed, already_enabled, not_enabled, plugin_start_failed.
- `capability_invoke{capability, input, deadline_ms}`: `input` objeto JSON ≤ 8 KiB
  (profundidade ≤ 4), `deadline_ms` 1..=10000. Resposta `ok` + `capability_result`
  no snapshot `{capability, plugin_id, ok, output|error, elapsed_ms}`. Códigos:
  unknown_capability, capability_unavailable (plugin parado/revogado/falho),
  invalid_input, capability_timeout, plugin_error, plugin_output_invalid, busy
  (uma invocação por plugin por vez, fila 0), invoke_cancelled.
- `capability_cancel{capability}`: cancela invocação ativa (envia cancel ao
  plugin; Core responde invoke_cancelled mesmo se plugin ignorar).

Snapshot `plugins`: `{revision, items:[{plugin_id, semver, capabilities,
state: disabled|starting|running|failed|stopped|quarantined, enabled,
restarts, last_error}]}`; `capability_result` último resultado (limpo ao
desabilitar/revogar). Eventos Core: plugin_enabled, plugin_started, plugin_stopped,
plugin_failed, plugin_disabled, plugin_revoked, capability_invoked.

## Processo e sandbox

Core inicia com `--plugin-python ABS_PYTHON` (obrigatório para ativar; ausente ⇒
plugin_not_runnable). Cada plugin = 1 processo `ABS_PYTHON -I /plugin/main.py` em
bwrap: `--unshare-all` (sem rede), `--die-with-parent`, `--ro-bind` do runtime
Python e do payload verificado (arquivo único em /plugin/main.py), `--tmpfs /tmp`,
sem HOME/XDG do usuário, env limpo, stdin/stdout = protocolo, stderr descartado,
limites (RLIMIT_AS ≤ 512 MiB, RLIMIT_CPU ≤ 30 s por processo, RLIMIT_NOFILE ≤ 32,
RLIMIT_NPROC = processos do uid no spawn + 256, com 1 retry em EAGAIN; RLIMIT_CPU de vida 3600 s
com orçamento de 30 s POR invocação medido pelo host; `--cap-drop ALL`; /tmp com teto de 64 MiB;
ver o Resultado C1 e docs/evidence/c1-llm.json para o endurecimento aplicado). O payload é
re-hasheado imediatamente antes do spawn e ligado por CAMINHO (janela TOCTOU residual
conhecida; o plano era abrir fd verificado e passar por bind do
caminho namespace 0600 após re-verify). Falha de spawn ⇒ failed; no máximo 1
reinício automático por habilitação; depois failed até nova ação do usuário.
Shutdown do Core e disable/revoke: `shutdown` ao plugin, SIGKILL após 1 s, wait
(sem zumbis, kill_on_drop). Idle: sem timers de polling; plugin parado não consome.

## Protocolo plugin ↔ Core (JSON-lines v1, linha ≤ 64 KiB, UTF-8)

Core→plugin: `{"v":1,"id":N,"op":"hello","plugin_id":…}` →
`{"v":1,"id":N,"ok":true,"plugin_id":…,"api":1,"capabilities":[…]}`; Core confere
plugin_id e capabilities ⊆ manifest (senão failed `handshake_mismatch`); hello em
≤ 3 s. `invoke{id,capability,input,deadline_ms}` → `{id,ok:true,output}` ou
`{id,ok:false,error:"código_snake"}`; output objeto JSON ≤ 8 KiB (profundidade ≤ 4);
resposta sem id correspondente/duplicada/oversize/lixo ⇒ plugin_output_invalid e
plugin failed. `cancel{id}`, `shutdown`. Plugin→Core pode emitir
`{"event":"log","level":"info","text":≤200}` (rate limit 10/s, descartado silenciosamente
acima; vira evento plugin_log no máximo 20 por minuto, texto só PlainText).
