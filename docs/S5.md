# S5 — Connections e integrações (E1–E4)

Fonte: Notion "S5 · Connections e integrações". Gideon executa tarefas pelo caminho estruturado e autorizado
(API), nunca por wrapper de clique de browser. Agentes e Skills consomem capabilities sem ver OAuth/token/endpoint.
Neste ambiente NÃO há credenciais reais autorizadas para estes serviços: todo conector é exercitado contra
SERVIDORES FALSOS em loopback (fixtures). As chaves de LLM do dono NÃO são usadas em S5. Credenciais/contas reais
→ AWAITING_HUMAN_VALIDATION.

## E1 — Connection Manager (Core, `src/connections.rs`)

- **Provedores** = descritores FIXOS no Core (dados compilados, não plugin): `github`, `google`, `homeassistant`, `mcp`.
  Descritor: `{id, scopes:[{id,label,access: read|write|destructive|public}], operations:[{name, scope, risk: read|write|destructive|public,
  method, path (template com {param}), params schema (tipos/limites), body schema, idempotent: bool, project: [campos permitidos na resposta]}]}`.
  Operações são o ÚNICO modo de falar com o serviço; resposta é projetada nos campos permitidos (≤ 4 KiB), nunca bruta.
- **Contas** (ledger `connections.json`, 0600, version 1, `revision` CAS, ≤ 8 contas, deny_unknown_fields):
  `{id, provider, label, account_ref (nome exibido devolvido pelo serviço), status: disconnected|connecting|connected|expired|offline|error|reauth_required,
  granted_scopes[], created, last_ok?}`. Segredos (token de acesso, refresh) ficam no cofre `secrets.json` (write-only, 0600,
  chave `conn:<id>:access|refresh`); nunca no ledger, snapshot, audit, skill ou plugin.
- **Autenticação simulada**: fluxo OAuth device-code contra o servidor falso (flag de teste `--connections-fake <provider>=<http://127.0.0.1:porta>`;
  sem a flag os provedores reais NÃO são contatados e `connection_connect` devolve `provider_unreachable`/`real_backend_unsupported`).
  Ops: `connection_add{provider,label}`, `connection_connect{id}` (inicia; passo de consentimento exibe `user_code` e escopos pedidos),
  `connection_consent{id, scopes[]}` (usuário concede POR ESCOPO; subconjunto do pedido), `connection_refresh{id}`, `connection_disconnect{id}`
  (apaga segredos, status disconnected), `connection_revoke{id}` (revoga no servidor falso + apaga), `connection_remove{id}`,
  `connection_call{id, operation, args}` (usado pelo UI de teste e pelos consumidores internos).
- **Chamadas** (`broker` existente com allowlist exata de host): orçamento de rede (≤ 30 chamadas/min por conta, ≤ 8 s por chamada, resposta ≤ 64 KiB),
  erros mapeados (`rate_limited` com `retry_after` ≤ 60 s, `unauthorized`→ tenta refresh 1x → `expired`/`reauth_required`, `forbidden_scope`,
  `account_mismatch` se o servidor devolve outro `account_ref`, `timeout`, `provider_error`), retries SÓ para operações `idempotent` (chave de
  idempotência enviada) e no máximo 2, backoff limitado. Risco: `read` executa; `write` pede aprovação do usuário (como tool_decide);
  `public`/`destructive` exigem aprovação explícita e, em desenvolvimento sem `--connections-allow-public`, ficam pendentes/falsos (nunca executam).
  Escopo não concedido ⇒ `scope_not_granted` sem chamada de rede.
- **Isolamento**: desconectar/falha de rede nunca afeta Core/voz/wake (testado). Dados escopados por conta; nada do conteúdo vai ao modelo/Skill sem passar
  pelo projetor. Audit sem conteúdo: `connection_added|connected|consented|refreshed|expired|revoked|call{operation,risk,outcome}`.
- **Snapshot** `connections`: `{revision, items:[{id,provider,label,account_ref?,status,granted_scopes,pending_scopes?,user_code?}], providers:[{id,scopes,operations:[{name,scope,risk}]}], last_call?:{operation,outcome,code?}}` (sem segredos/conteúdo).
- **Consumidores**: tools do agente C3 `connection_call` genérico NÃO existe; em vez disso entradas FIXAS no registro: `github_create_issue`, `github_list_repos`,
  `calendar_list_events`, `ha_get_state`, `ha_call_service`, `mcp_call` (cada uma vira `connection_call` com operação fixa; mesmas aprovações). Skills podem
  declarar `call: "conn:<provider>.<operation>"` em `dependency_capabilities` (D1 amend: prefixo `conn:`), resolvido pelo executor D2 com os mesmos checks.

## E2 — Conectores (um completo antes do próximo)

Cada conector: descritor + servidor falso (`tests/fixtures/connections/<provider>_server.py`, loopback, estado em memória) + autenticação simulada + erros +
revogação + E2E com Agent Runtime (LLM roteirizado → tool → aprovação → efeito verificado no servidor falso).
- **E2.1 github**: `repos.list`, `repo.get`, `issues.create` (write; público ⇒ `public` quando repo público), `issues.update`, `pulls.get`, `pulls.comment` (public), `actions.list`.
  Escopos `repo:read`, `issues:write`, `pulls:write`. Post público exige aprovação explícita.
- **E2.2 google**: sub-conexões escopadas `gmail.read`, `gmail.send`(public), `gmail.delete`(destructive), `calendar.read`, `calendar.write`, `drive.read`, `drive.write`; separação read/send/delete;
  backoff/quota (`rate_limited`), `reauth_required` quando escopo muda. Sem suposição de acesso gratuito/ilimitado: quota é do servidor falso e exposta como erro.
- **E2.3 homeassistant**: `states.list`, `state.get`, `service.call` com lista de serviços perigosos (ex. `lock.unlock`, `alarm_control_panel.*`, `cover.open`) ⇒ `destructive` (confirmação forte); base URL é só o fake em dev.
- **E2.4 mcp**: servidor MCP stdio falso rodando em bwrap (processo, sem rede, mesmo sandbox de plugin); `mcp.discover` (lista tools com JSON-schema validado: tipos simples, ≤ 16 tools, ≤ 2 KiB cada),
  `mcp.call{tool,args}` por ferramenta com confirmação individual, trust limitado (saída = dado não confiável, prefixada, nunca instrução; tool nova após discover exige re-aprovação), tools que alegam destrutivo/rede tratadas como `write`.

## E3 — Escolha do melhor caminho (CapabilityRegistry)

`src/registry.rs`: associa FINALIDADE (`create_issue`, `list_events`, `read_state`, …) a providers disponíveis e ordena por: autorização > segurança (menor risco) > suporte oficial >
confiabilidade (último resultado) > privacidade > menor efeito colateral. Rotas: `connection` (API) e `visual` (C4 sintético). Regras: usa a rota `connection` se conectada, com escopo
concedido e sem `expired`; fallback visual SOMENTE se a API não existe/não está disponível E o usuário habilitou explicitamente `visual_fallback` para a finalidade (op `registry_allow_visual{purpose}`, revogável)
E a ação de publicação foi aprovada; NUNCA fallback silencioso para contornar token ausente/expirado/escopo negado (retorna `route_unavailable` com motivo). Op `registry_plan{purpose}` devolve a rota escolhida e
descartadas com motivo (sem executar); o LLM não decide grants. Prompt injection em título/corpo de issue não altera rota, escopo nem aprovação. Efeito verificado relendo o servidor falso (id do issue).

crash/recovery; profiles; offline; demo E2E (PCM wake→Command→TTS virtual; instala plugin pelo Hub; LLM roteirizado gera tool call, skill draft e issue no GitHub falso). Auditoria P0/P1

`AWAITING_HUMAN_VALIDATION`. Gera `docs/HUMAN_VALIDATION.md` com checklist consolidado para o dono.

## Resultado E2.2 google (AUTO_VERIFIED contra servidor falso)

- `src/connections.rs`: descritor `google` com 7 escopos (`gmail.read` leitura, `gmail.send` público, `gmail.delete` destrutivo, `calendar.read`, `calendar.write`, `drive.read`, `drive.write`) e 7 operações: `gmail.messages.list` (read), `gmail.send` (public), `gmail.messages.delete` (destructive), `calendar.events.list` (read), `calendar.events.create` (write, idempotente), `drive.files.list` (read), `drive.files.create` (write). Projeções: listas só `id`, `from`, `subject` (ou `name`, `title`, `start`, `end`); nunca corpo ou conteúdo.
- Ferramentas fixas do agente, só com `--connections-fake google=<url>`: `calendar_list_events`, `gmail_list_messages`, `calendar_create_event`.
- Gate `scripts/verify_e22_google.py`: 111 passed, 0 failed, 4 skipped (device codes no vazamento, timeout e refresh rejeitado cobertos por github/Rust, orçamento de rede coberto por Rust). Evidência `target/evidence/e22-google.json`. Regressão `verify_e1_connections.py`: 119/0 (2 skips).
- Rust: `tests/connections.rs` com 12 testes google (servidor falso real `google_server.py`); unitários com projeção e validação de valores. Suíte completa: 323 passed, 0 failed.
- Emendas ao contrato (código é a autoridade):
  - Escopo perdido no refresh: a conta vai a `reauth_required` e mantém só os escopos ainda concedidos. Chamada que precisa do escopo perdido responde `scope_not_granted` sem rede; chamada com escopo mantido responde `reauth_required`. A chamada que disparou o refresh falha com um desses códigos.
  - `reauth_required` mantém `granted_scopes` (antes eram limpos). Vale também para github: o que o usuário concedeu continua listado até reconectar.
  - Novos códigos de conexão com texto no Core/UI: `not_found`, `public_disabled`, `scope_not_requested`, `device_expired`, `consent_denied`, `connections_storage_error`.
  - Argumentos novos: `id` (1–64 bytes `[A-Za-z0-9_-]`, vai no caminho), `to` (um endereço), `start`/`end` (RFC 3339 com segundos e `Z` ou ±HH:MM), `name` (1–128 bytes sem `/`, `\`, `.` ou `..`), `content` (até 8 KiB).
  - 429 (`rate_limited` ou `quota_exceeded`) vira `rate_limited` com `retry_after` de 1 a 60 s. O Core não espera sozinho (mesmo comportamento do github); quem chama aguarda.
  - Idempotência: só `calendar.events.create` envia `Idempotency-Key` e repete em 5xx ou timeout (até 2 vezes, mesma chave). `gmail.send`, `gmail.messages.delete` e `drive.files.create` nunca são repetidos.
  - Broker: `DELETE` entra na allowlist de métodos (`scripts/net_broker.py`), com o mesmo host exato e cabeçalhos.
- Fixture: `POST /__control/fail_after_create {n}` (teste) em `google_server.py`, documentado no README.
