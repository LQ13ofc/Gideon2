# S3 / C2 — LLM Model Manager (somente dentro do plugin LLM)

Fonte: Notion "S3 · Plugins e LLM Engine" (Gate C2) e a política de modelos. O gerenciador de
modelos de LLM mora no plugin `llm_engine`; a Base não ganha catálogo, perfil, métrica nem
gerenciador de modelos. STT/TTS/Wake nunca aparecem aqui. Nenhuma marca é dependência dura.

Gate C2 (Notion): escolher modelo local ou remoto (simulado), persistir, reiniciar,
desinstalar/reinstalar, LKG/rollback; cofre de chaves e fallback nunca mandam conteúdo à nuvem
sem opt-in; tool exigida + LLM só-texto ⇒ UNAVAILABLE. Compatibilidade "total" só com matriz
certificada por modelo/backend/hardware; nada de promessa universal.

## Infraestrutura genérica no Core (não é gerenciador de modelos)

1. Provedores locais além dos remotos: `local` (servidor llama.cpp, OpenAI-compatível,
   `http://127.0.0.1:<local_port>/v1`) e `ollama` (`http://127.0.0.1:<local_port>/v1`, padrão 11434).
   Somente host `127.0.0.1` exato, porta 1024..=65535, http permitido (loopback), SEM exigir
   consentimento de nuvem e SEM chave; nunca resolvem DNS. `llm_configure` ganha `local_port`
   (u16, obrigatório para local/ollama, ignorado nos demais). `--net-allow-loopback` continua
   só para o provedor `custom` em testes.
2. Último-bom-conhecido: o ledger llm-config guarda `lkg` (provider, model, custom_url,
   local_port, cloud_consent ao marcar). Ops: `llm_mark_good{revision}` (promove a configuração
   atual a LKG) e `llm_rollback{revision}` (restaura LKG; sem LKG ⇒ `no_lkg`). Snapshot
   `llm.config.lkg` (objeto|null). Revisão CAS própria `llm_revision` (já existe).
3. Fallback autorizado: config ganha `fallback` (null | {provider, model, custom_url?, local_port?})
   com as mesmas validações. O plugin só pode usar `target:"fallback"` em `host_call`; o Core exige
   para um fallback de NUVEM: consentimento (`cloud_consent`) e chave do provedor, senão
   `cloud_not_authorized`/`key_missing`; fallback local não exige. Nunca há fallback implícito
   no Core: quem decide tentar é o plugin, só após erro recuperável, e cada tentativa é um
   `host_call` explícito auditável (evento `llm_fallback_used`, sem conteúdo).
4. Armazenamento de configurações do plugin (genérico): serviços `settings.get` e `settings.put
   {data: objeto ≤ 8 KiB, profundidade ≤ 4}` via host_call, ledger `plugin-settings/<plugin_id>.json`
   0600 (strict, atômico, fsync, ≤ 16 KiB), exige permissão aprovada `storage_settings`. Os dados
   sobrevivem a desinstalar/reinstalar; op `plugin_settings_clear{plugin_id}` apaga por pedido do
   usuário. O Core nunca interpreta o conteúdo.
5. Códigos de erro adicionais repassados (allowlist): `model_unsupported_feature`,
   `model_not_found`, `model_selftest_failed`, `settings_unavailable`.

## Plugin llm_engine 1.1.0 (o gerenciador)

Permissões: `network_llm`, `storage_settings`. Capabilities: `llm_engine.chat` (compatível com
C1; novo campo opcional `require: ["tools","streaming","vision"]` e `fallback:true|false`) e
`llm_engine.models`.

`llm_engine.models` input `{action, ...}` (≤ 8 KiB), ações:
- `list {tab:"recommended"|"custom", offset:int≥0, limit:1..=6}` ⇒ `{tab, items:[Model], total:int, offset:int, selected:{provider,model}|null, hardware}` (paginado: a saída do plugin tem teto de 8 KiB e um Model completo tem ~0,5 KiB; a UI pede páginas e mostra "Carregar mais"; nenhum modelo fica invisível).
- `describe {id}` ⇒ `{model: Model}` (envelope).
- `selftest {}` ⇒ (o resultado sondado é PERSISTIDO em settings em `probes`, chave provider|model|port, ≤ 32 entradas, e passa a compor a matriz efetiva; vision continua `unknown`) testa a configuração SELECIONADA no Core (ctx): 1 chat curto em streaming + 1
  sonda de tool use; devolve `{ok, latency_ms, features:{streaming,tool_use,vision,cancel,context_tokens},
  source:"probed"}` ou erro `model_selftest_failed` com o código real do provedor. Vision nunca é
  sondada (permanece `unknown`).
- `save_custom {model}` / `delete_custom {id}` (≤ 16 custom; validação estrita; persiste em settings).
- `features {}` ⇒ matriz de recursos efetiva do modelo selecionado (certificado ∪ declarado ∪ sondado).

`Model`: `{id (≤64), label, kind: local|cloud, provider: openrouter|opencode|google|custom|local|ollama,
model (id do provedor), tier: recommended|custom, license, quantization|null, sha256|null (GGUF),
backend, features:{streaming,tool_use,vision,cancel: supported|unsupported|unknown, context_tokens:int|null},
certification: {state: certified|candidate|declared|probed, evidence: str|null, date|null},
cost: {input_per_mtok|null, output_per_mtok|null, currency:"USD"|null}, latency_hint: low|medium|high|unknown,
min_hardware: {ram_gb|null, gpu: none|optional|required|unknown}, offline: bool}`.
Regras: só `certified` pode ser exibido como "Certificado"; cada recurso certificado cita
evidência real (arquivo/gate). Catálogo recomendado embutido no payload do plugin (dados, com
hash coberto pelo catálogo do Hub). Honestidade: gemini-3.5-flash-lite e ministral-3b-latest têm
streaming e tool_use `supported` com evidência do gate C1 live; modelos locais (llama.cpp/GGUF,
Ollama) entram como `candidate` até serem certificados em hardware real; custo só quando conhecido.
`hardware`: `{cpu_cores, ram_gb, gpu:"unknown"}` lido de /proc no sandbox (sem detecção de GPU).

Regra de indisponibilidade: se `require` contém recurso que a matriz do modelo selecionado marca
`unsupported` ⇒ erro `model_unsupported_feature` (UI: INDISPONÍVEL com o recurso faltante, sem enviar
nada ao provedor). Recurso `unknown` ⇒ tenta e, se o provedor recusar, reporta o erro real.
Fallback: após erro recuperável (`http_error` 429/500/502/503/504, `network_unavailable`, `timeout`)
e `fallback:true` e fallback configurado, repete UMA vez com `target:"fallback"`; saída marca
`used_fallback:true`; erros não recuperáveis (key_missing, cloud_not_authorized, 401/402/403,
permission_denied) nunca disparam fallback.

## UI (Qt) — página "Modelos LLM"

Só aparece com o plugin llm_engine em execução (a Base não tem aba de modelos). Abas
"Recomendados" e "Personalizados", filtro Local/Nuvem, lista com selo de certificação, detalhes
(licença, quantização, hash, recursos, custo, latência, hardware mínimo), botão "Usar este modelo"
(fluxo: llm_configure → selftest → ok ⇒ llm_mark_good; falha ⇒ llm_rollback e mensagem),
formulário "Adicionar modelo personalizado" (provedor/modelo/porta ou URL https, recursos
declarados), "Remover", estado do modelo atual (Disponível | INDISPONÍVEL: recurso X
não suportado | Sem chave | Sem consentimento), painel de hardware e seleção de fallback com
aviso de nuvem. Nada aqui muda wake/STT/TTS.
