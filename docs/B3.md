## B3.1 — catálogo e descoberta

Core carrega explicitamente --hub-catalog ABS_JSON SHA256, uma vez no boot.
Catálogo v1 com até 8 manifests, máximo 64KiB, JSON estrito; arquivo regular
aberto O_NOFOLLOW/O_NONBLOCK, leitura bounded e hash antes de desserializar.
Repository/build source/binários são URLs GitHub HTTPS declaradas, sem fetch.
Campos mínimos do manifest: plugin_id, api_version, publisher, semver, targets,
binaries(url/target/sha256/size), license, permissions, dependencies(id/version),
conflicts, entrypoint relativo, build_source, support_policy, signature opcional.
Assinatura declarada NÃO verificada nesta microetapa; publisher_verified=false.
Nada fornece grants. Checksums do catálogo não provam confiança no publisher.

Formato restrito de IDs/semver MAJOR.MINOR.PATCH/paths/URLs/ranges/duplicatas e compatibilidade API/
target/dependencies são decididos no Core. Snapshot sem caminhos privados;
not_installed ou incompatible + reason, nunca installed por constar no catálogo.
Catálogo inválido entra quarantined/entries vazio sem impedir áudio/comandos Base.
Hub ausente não altera perfil antigo. UI Plugins lê snapshot validado, sem botão
de instalação funcional até B3.2 e sem painel Models.

Gate: fixtures reais de arquivo/hash/links/tipos/ranges/metadata/compatibility,
daemon real e UI offscreen exibem os mesmos fatos; catálogo corrompido não quebra
S1; sem download/processo plugin; regressões anteriores no mesmo release.
