## B3.1 — catálogo e descoberta

Core carrega explicitamente --hub-catalog ABS_JSON SHA256, uma vez no boot.
Catálogo v1 com até 8 manifests, máximo 64KiB, JSON estrito; arquivo regular
aberto O_NOFOLLOW/O_NONBLOCK, leitura bounded e hash antes de desserializar.
Repository/build source/binários são URLs GitHub HTTPS declaradas, sem fetch.
Campos mínimos do manifest: plugin_id, api_version, publisher, semver, targets,
binaries(url/target/sha256/size), license, permissions, dependencies(id/version),
conflicts, entrypoint relativo, build_source, support_policy, signature opcional.
Assinatura declarada NÃO verificada nesta microetapa; publisher_verified=false.
Nada fornece grants. Checksums do catálogo não provam confiança no publisher.

Formato restrito de IDs/semver MAJOR.MINOR.PATCH/paths/URLs/ranges/duplicatas e compatibilidade API/
target/dependencies são decididos no Core. Snapshot sem caminhos privados;
not_installed ou incompatible + reason, nunca installed por constar no catálogo.
Catálogo inválido entra quarantined/entries vazio sem impedir áudio/comandos Base.
Hub ausente não altera perfil antigo. UI Plugins lê snapshot validado, sem botão
de instalação funcional até B3.2 e sem painel Models.

Gate: fixtures reais de arquivo/hash/links/tipos/ranges/metadata/compatibility,
daemon real e UI offscreen exibem os mesmos fatos; catálogo corrompido não quebra
S1; sem download/processo plugin; regressões anteriores no mesmo release.

## B3.2a — aprovação vinculada ao manifest

HubApprove v1: revision u64, plugin_id, manifest_sha256, permissions exatas do
manifest e publisher_unverified_ack bool explícito. Metadata canonical serde
SHA256 + checksum do catálogo pinado vinculam a aprovação; isso não autentica
publisher e não concede grants aos comandos Base. Snapshot expõe approval_revision
e permissions_approved; nenhum status installed ou runtime é criado.

Idle/ready/request dedup; unknown/incompatible/mismatch/no-ack/stale rejeitados.
Arquivo hub-approvals.json privado (uid/0600/nlink1/O_NOFOLLOW/O_NONBLOCK), JSON
estrito bounded 16KiB/8 registros. Escrita atômica comparte primitive com config;
failure antes de rename preserva original. Core recarrega fato persistido antes
de responder, inclusive falha de fsync pós-rename. Conteúdo/caminho inválido
coloca somente Hub em quarentena; Base continua. Troca de catálogo/hash não herda
aprovação. Revisão não é resetada na troca de catálogo.

Qt mostra review separado, acknowledgement inicialmente desmarcado, botão sem
ack desabilitado. Testes automatizados aprovam só fixture benigna em root efêmero;
não pedem ao usuário e não aprovam capability real de computador. Persist/restart,
bytes/perms/security/falhas/busy/invalid e Core/Qt/nativo integrados são o gate.
Importação de bytes/staging permanece B3.2b; B3.2a não afirma plugin instalado.

## Contrato B3.2b — importação opaca em staging

Core recebe HubBegin(revision,plugin_id,manifest_sha256), HubChunk(import_id,
offset,hex), HubFinish(import_id), HubAbort(import_id) pelo mesmo IPC privado.
Core gera import_id com epoch de boot e sequência de eventos; uma importação ativa; offsets exatos,
blocos 1–1024 bytes hex lowercase, teto pelo binário do target (máximo 64MiB).
120s absolutos, sem timer polling em repouso. Begin/chunk/finish rejeitam sessão
ocupada; abort continua disponível. Dedup, unknown fields e Ready mantidos.

Fonte pertence ao cliente; Core nunca abre path enviado, URL ou entrypoint.
Approval exata vigente é revalidada no begin e finish. Staging usa arquivo novo
0600, nome derivado do digest do manifest, root privado existente. Finish confere
size/hash incremental e rehash do descriptor, identidade do path, fsync e rename
no-clobber Linux. Não extrai archives, instala ou executa. Payload verificado
opaco reaparece como payload_staged após restart (private fd/size/hash rechecados).
Não vira status installed nem autentica publisher. Cancel/failure/timeout/shutdown
remove apenas pending pertencente ao fd; pending órfão de crash bloqueia reimport
sem autoapagamento. Corrupção do payload existente põe somente Hub em quarentena.

Gate: IPC e cliente reais, aprovação ausente/alterada, tamanho/hash/offset/hex,
traversal/unknown fields, symlink/hardlink/FIFO/perms, cancel/stale/busy/timeout,
shutdown/restart, atomic no-clobber/pending collision, Qt e regressões Base.
Atualização/rollback/remove e execução isolada de fixture continuam B3.3.

## Contrato B3.3 — ciclo install/update/rollback/remove/quarantine

Instalar = promover payload opaco staged e verificado para namespace privado do
Core; nada é extraído, carregado ou executado. Runtime de plugin fica sempre
"disabled" até S3. Publisher continua não autenticado; nenhum grant Base.

Namespace: `<root>/hub-plugins/` (dir 0700, dono, não symlink). Arquivo por
versão `<plugin_id>-<manifest_sha256>.payload` 0600, nlink 1. Ledger privado
`hub-installed.json` (≤16KiB, deny_unknown_fields, version 1, revision u64 CAS
própria `install_revision`, ≤8 records). Record: plugin_id, semver,
manifest_sha256, payload_sha256, size, previous opcional {semver,
manifest_sha256, payload_sha256, size}. Escrita = replace_json atômico + fsync
do root, mesmo padrão de hub-approvals.json. Ledger é a fonte de verdade.

IPC (mesmo dedup/unknown fields/version; Ready; sessão de voz → busy; importação
ativa → hub_import_busy; revision != install_revision → stale_install_revision):
- hub_install(revision, plugin_id, manifest_sha256): entry do catálogo atual
  compatível, manifest exato, approval exata vigente, payload_staged reverificado.
  Move staged → namespace com renameat2 NOREPLACE; commit ledger; ativo antigo
  vira previous (update); previous mais antigo é removido após commit.
  Eventos hub_plugin_installed ou hub_plugin_updated.
- hub_rollback(revision, plugin_id): exige previous verificável; troca
  ativo↔previous só no ledger. Evento hub_plugin_rolled_back.
- hub_remove(revision, plugin_id): commit ledger sem o plugin, depois unlink
  somente dos arquivos nomeados pelo record. Funciona também em quarantined.
  Evento hub_plugin_removed.

Snapshot: `install_revision`, `installed[]` {plugin_id, semver,
manifest_sha256, state installed|quarantined, runtime "disabled", previous
{semver, manifest_sha256}|null}. Entry status ganha installed (manifest igual ao
ativo) e update_available (plugin instalado com outro manifest); approval vale
para not_installed e update_available. Startup/refresh verificam cada arquivo do
ledger (privado, tamanho, hash); falha põe só aquele plugin em quarantined
(rollback recusado, remove permitido). Ledger inválido/inseguro → Hub quarantined;
Base continua. Arquivos órfãos no namespace nunca são apagados automaticamente;
colisão em install falha fechado (hub_storage_error).

Gate: fixture benigna instalada/atualizada (catálogo v2 pinado no restart)/
revertida/removida em root efêmero; hashes/perms/symlink/hardlink guards;
quarantine de payload adulterado sem derrubar Base; restart preserva estado;
Qt real mostra instalado/desativado e ações; S1 nativo antes/depois e regressões.
