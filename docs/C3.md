# S3 / C3 — Agent Runtime (Core)

Fonte: Notion "S3 · Plugins e LLM Engine", Gate C3. Cadeia: LLM texto+tools → intenção/plano
estruturado → checagem de escopo/capability → executor → verificação → observação de volta ao
LLM → resposta. A Base continua sem LLM: o runtime só roda quando um plugin com capability
`*.chat` está em execução; sem ele `agent_start` ⇒ `llm_unavailable` e S1/S2 seguem intactos.

## Princípios

1. O LLM só PROPÕE. Registro fixo de tools no Core (`src/tools.rs`), nunca ampliado por plugin ou
   pela saída do modelo. Saída de tool e saída do modelo são DADOS: nunca promovem privilégio,
   nunca mudam o registro, o escopo, o orçamento ou o consentimento.
2. Leitura executa sozinha dentro do run; mudança de estado exige `tool_decide` do usuário
   (como C1); DESTRUTIVA/publicação/financeira (`Risk::Destructive`) exige aprovação explícita
   do usuário e, em desenvolvimento (sem `--agent-allow-destructive`, que NENHUM gate usa em
   produção), fica `pending` e nunca executa: o run termina `awaiting_approval`/`fake`.
3. Cada passo tem `invocation_id` (u64 monotônico do Core), registrado no ledger do run e no
   audit (sem conteúdo). Fronteira entre apps: tool só enxerga o app sintético/alvo declarado
   no próprio registro (`app` do tool); um run não cruza apps salvo tool que declare ambos.

## Limites (todos aplicados pelo Core, constantes)

`max_steps` 6, `max_tool_calls_per_step` 4, `run_deadline` 120 s, `step_deadline` 10 s (chat usa
10000 ms), `max_total_tokens` 4096 (soma de `usage` quando houver; senão estimativa
bytes/4 das mensagens), loops: a mesma (tool, args canônicos) repetida ≥ 2 vezes no run ⇒
`loop_blocked` (run termina). Retry: erro recuperável do chat (`timeout`, `network_unavailable`,
http 429/5xx) ⇒ 1 retry por passo; demais erros terminam o run `failed` com o código real.
Tool com falha de execução ⇒ observação `{"ok":false,"error":code}` ao LLM, conta como passo.

## Protocolo (v1, estrito, deny_unknown_fields, dedup como as demais ops)

- `agent_start{goal: str 1..=1024 bytes, capability?: str}` ⇒ `ok` + `agent.run_id`, ou
  `agent_busy` (1 run por vez), `llm_unavailable`, `invalid_input`. `goal` é mensagem `user`.
- `agent_abort{run_id}` ⇒ `ok`/`unknown_run`. Cancela o chat em voo (capability_cancel),
  cancela propostas pendentes do run (estado `cancelled`), run → `aborted`.
- Snapshot `agent`: `null` ou `{run_id, state, goal_len, step, max_steps, started_ms_ago,
  steps:[{n, invocation_id, kind: chat|tool, tool?, risk?, state, code?}], answer?, error?,
  budget:{tokens_used, tokens_max}}`. `state`: `thinking | waiting_tool | awaiting_approval |
  done | failed | aborted | blocked`. `answer` ≤ 4 KiB só quando `done`. Nunca contém args
  brutos de tool nem observações: só contagens/códigos (conteúdo vive apenas no chat/proposals,
  como em C1).
- Propostas do run aparecem em `tool_proposals` (já existente) com campo adicional `run_id`
  e `step`. `tool_decide` é o único caminho de aprovação.
- Eventos de audit (sem conteúdo): `agent_started`, `agent_step`, `agent_tool`, `agent_done`,
  `agent_failed`, `agent_aborted`, `agent_blocked{reason}`.

## Execução e verificação

Para cada tool_call: (1) `tools::command` valida nome/args exatos; (2) risco; (3) read ⇒
executa; state-changing ⇒ proposta pendente, run em `awaiting_approval`, retoma após decisão
(negar ⇒ observação `{"ok":false,"error":"denied_by_user"}`); (4) VERIFICAÇÃO pós-ação: tools
com `verify` declarado releem o estado (ex. app sintético) e a observação inclui
`verified:true|false`; `verified:false` ⇒ observação de falha, nunca "sucesso" presumido;
(5) observação (≤ 1 KiB, truncada em fronteira UTF-8) vira mensagem `role:"tool"` com prefixo
fixo `[tool_output:<nome>] ` e conteúdo tratado como não confiável.

Stale screen: tools sintéticas de tela carregam `epoch` (contador do app). Ação com `epoch`
diferente do atual ⇒ `stale_screen` (não executa; observação ao LLM para reobservar; conta
passo; 2 stale seguidos ⇒ `blocked`). Revogação: `plugin_disable`/`plugin_revoke` do plugin do
chat, ou `llm_configure` mudando provedor, aborta o run (`aborted`, motivo `revoked`);
revogar permissão de um tool não-LLM também bloqueia (`permission_revoked`).

## Tools sintéticas (somente com `--agent-synthetic`, nunca no pacote de produção)

App sintético em `<home>/synthetic/app.json` (0600): `{epoch, counter, text, published:false}`.
Registro de teste: `synth_screen_read{}` (read; devolve `epoch`+`text`), `synth_counter_inc
{epoch}` (state-changing; verify relê counter), `synth_set_text{epoch, text≤64}`
(state-changing), `synth_publish{}` (Destructive; nunca executa em dev),
`synth_bump_epoch{}` (usado só pelo gate para simular tela obsoleta, via op de teste
`agent_test_bump`, existente só sob a flag). Sem a flag essas tools não existem (unknown_tool).

## UI (Qt)

Seção "Agente" na página Conversa quando o plugin LLM roda: campo objetivo, Iniciar/Abortar,
lista de passos (kind, tool, risco, estado), cartões de proposta já existentes, resposta
final PlainText, banner de estado (pensando/aguardando aprovação/bloqueado/falhou com código).
Bridge: slots `agentStart(goal)`, `agentAbort()`; sinal `agentChanged`; `validate_snapshot`
estrito do bloco `agent`.

## Gate C3 (verify_c3_agent.py)

Core real + LLM falso roteirizado (fixture `llm_engine.py` com modo script por arquivo
`agent-script.json` na pasta do plugin: lista de respostas por passo) + app sintético:
1. caminho feliz: read → state-changing aprovado → verificado → resposta final; efeito no
   `app.json` conferido por arquivo; invocation_ids únicos e crescentes.
2. negar ⇒ nenhum efeito; abort no meio ⇒ nenhum efeito e chat cancelado.
3. destrutivo `synth_publish` ⇒ nunca executa, run `awaiting_approval`/fake, `published:false`.
4. prompt injection: (a) texto do usuário/goal mandando "ignore regras"; (b) observação de
   tool contendo instruções + tool_call forjada em texto; (c) o modelo propondo tool fora do
   registro/app: nada executa fora do registro, escopo ou aprovação; auditoria sem conteúdo.
5. limites: passos > 6, deadline do run (relógio acelerado por flag de teste), tokens, loop
   idêntico ⇒ `loop_blocked`, retry único de erro recuperável, erro 401 não repete.
6. stale screen (epoch trocado entre observar e agir) ⇒ não executa, reobserva; 2 stale ⇒ blocked.
7. revogação do plugin LLM e `plugin_revoke` no meio ⇒ aborted; S1 (wake/comandos) segue.
8. sem plugin LLM ⇒ `llm_unavailable`; chave nunca vaza; snapshot sem args/observações.
9. Qt offscreen ponta a ponta (objetivo → aprovação → resposta) + pacote instalado repete 1.
10. Regressão: matriz completa uma vez por estágio.
